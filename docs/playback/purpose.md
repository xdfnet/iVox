# 播报目的层

> **取舍听它的。** 它回答：**播报为什么存在，以及遇到取舍时听谁的。**
> 机制看不懂先翻 [paper.md](paper.md)（比喻层），它建立直觉但不裁决。
> 它不描述系统，只裁决。其余三层遇到争议翻上来：
> [接入方层](sources.md)（谁在说话）·
> [需求层](requirements.md)（必须做到什么）·
> [实现层](queue.md)（怎么做到）。
>
> 每条原则下面都记着**它裁决过什么**——只有裁决记录的原则才算数，光是好听的口号一律不作数。

## 一、即时反馈优先

**用户在等 AI 的时候，默认要有声音。** 宁可少说，不可无声。

- **裁决过**：「页要不要等整页写完再出声」——否。分层流式，宁可让页多一个「还在来」的状态，
  也不能让用户在等的时候干听。实测 Claude 每 0.1～0.5 秒就来一行，整页等完能等十几秒。
- **裁决过**：「统一三个接入方的交付时机」——统一的是**结构**（摞→页→块），
  不是**时机**。时机统一就会牺牲即时出声，不值。

## 二、打断权只归用户

**动手的只有人。机器最多借道，借完就走。**

- **裁决过**：新回复到达时要不要打断在播——否。改成按到达序排队、播全播完。
  理由不是礼貌，是实测：一次 868 字长回复被 199ms 后到达的 84 字短回复整条掐掉。
- **裁决过**：Cmd+D 译文要不要清场——否，只临时插队，念完原顺序恢复。
- **裁决过**：hook 的「提交即打断」分支——删。打断只由快捷键承担。
- **裁决过（2026-10-17，18:52 翻车之后）**：**「用户正在听哪一摞」只能由设备已出声的位置
  回答，绝不由合成/排队进度回答。** 用户按了 Ctrl+1，他动手的结果就必须由他决定；
  名义上打断权在他手里、实际不在，名存实亡。当时的起点取自合成进度，那东西领先真实发声
  2~4 秒，于是掀掉的是队列里下一个还没出声的摞——正是他刚说过不要的那一摞。
  配套裁决：`dataConsumed` 领先真实发声 10~21ms **接受**，误差方向是安全的
  （指向正在响的，不指向还没响的）；要对齐得挂 `AVAudioEngine` tap，新增 IO 抖动风险，
  与收益不成比例。

## 三、不凑合

**要么做对，要么不做。半成品比不改更糟。**

- **裁决过**：「先加游标、容器留在队列里，之后再搬」——否。分步的每一版都是
  「队列仍然认摞」的将就形态，最后两套并存谁也不敢删。
- **裁决过**：「桶和摞各自定义一套」——否。两个词各说各的必然打架。
- **裁决过**：`playingPageID` 这种「顺手清一下就行」的写法——它就是陈旧靶心 bug 的成因。
- **裁决过（2026-10-17）**：「播完了但容器里还留着」这个将就形态——不留。
  容器原先只增不减，听完的摞一直占着位置，于是 ① 对外报告的「正在听哪摞」在播完之后还在撒谎；
  ② 更要命——播完后用户随手按 Ctrl+1，起点落在那个早已播完的摞上、给它立了墓碑，
  而 Claude 那一摞往往**还在继续送页**（一次输入 = 好几页），墓碑一立，后续页全被静默丢弃。
  现在每次泵顺手回收「已听完且已收尾」的段（判据是发声点，不是排队进度），收尾那条
  已确认真静音的路径连正在响的最后一块也一起清。
- **裁决过（2026-10-19）**：「MLX 崩了是 iVox 的 bug，所以修 iVox」——**修不了就隔离**。
  Metal 命令编码器析构时重复释放 GPU 命令队列直接 SIGTRAP，上游（mlx-audio-swift /
  mlx-swift）本地即最新、无新提交，encoder 又由 `generateStream` 内部创建、Swift 侧拿不到引用，
  **无从拦截**。同一个病根此前已经露过两次脸（取消时 commit 未收口、copy_gpu SIGSEGV），
  每次都打了个补丁在**特定路径**上苟住，第三次照旧炸——说明「在会炸的东西上打补丁」这条路本身
  就不成立。所以把 MLX 整个搬进子进程（誊清员），主进程不碰它、也不因它崩。
  **判据：一个依赖崩了且修不动，不等于本项目要跟着它一起崩；把它圈出去，比给它加判据更划算。
  隔离顺带买到「谁没干好一眼可见」——崩在哪个进程，日志就落在哪个文件。**
- **裁决过（2026-10-18）**：「无编号内容并进同一段」这个图省事的合并——**段就是摞**，
  无编号的稿一份单独开一段。原实现把没 turn_id 的稿子全塞进队尾那个无编号段，于是
  **不同时间的多次回复被焊成一摞**：Ctrl+1 的契约是「掀掉你此刻在听的这一摞，
  从下一摞接着播」，焊成一摞后「下一摞」根本不存在，按一次等于全掀
  （18:11 实测：掀掉 34 块，其中只有 6 块是新回复，其余 28 块是上一条长回复的余量）。
  Claude 因为每条回复都带 turn_id 走另一条路径，一直没踩到，所以这个洞藏了很久。
  **理由**：turn_id 只是摞的**编号**，不是摞**存在**的前提——段这个结构本身就表达了「一摞」，
  没有编号也要能独立成摞；编号额外换来的只有「立墓碑拦这一摞后续增量」那一个能力。
  **判据：谁定义了「摞」，谁就得保证「掀摞」在所有输入形态下都成立。无分组是一条被
  明确支持的入队路径（`ivox speak` / hook 终稿 / Cmd+D 译文全走它），不是 edge case，
  不能让它退化成「掀一次全丢」。**

## 四、服务不了目的的结构不进术语

**一个说法若只说得清「代码里是什么」、说不清「为了什么」，它就是歧义的温床。**

- **裁决过**：「桶」曾是第四个术语——它是队列的排队单位，用户从不按它操作。
  拿实现语言描述语义，「一摞 = 一桶」于是自相矛盾。降级为实现词。
- **裁决过**：动词集曾经有「读下一页 / 跳整摞 / 掀桌 / 撕 / 翻 / 丢弃 / 清场」七套说法——
  同一套动作混比喻和实词。收成「掐」「掀」两个。
- **裁决过**：「身份强弱分三档」这类只描述实现的说法——按用户能做什么来分
  （能不能掀页、能不能掀摞）。
- **裁决过（2026-10-17）**：用户措辞里的**「当前」**——删。三档打断改说成
  「我不想听这页了，听下一页 / 我不想听这摞了，听下一摞 / 当前盖上的摞都不听了」。
  理由：说「掀当前那一摞」就等于要求代码维护一个「当前是谁」的状态，而那个状态正是
  这次翻车的载体；改说「听下一摞」之后，起点只需回答「用户耳朵里那摞是谁」，
  这个问题有唯一真源，不与合成进度纠缠。**判据：一个词如果逼着代码去维护一个
  实现层的陈旧状态，它就不该出现在用户话里。**
- **裁决过（2026-10-17）**：一个概念不兼职两职。旧代码里「游标」既是**队列进度**
  （已排进播放器）又是**用户感知位置**（用户耳朵里那摞），两者相差 2~4 秒却共用一个数，
  这正是病灶。现在拆成两个数：`cursorSeq`（队列进度，消费层用）与
  `audibleSeq`（发声点，干预层用）。**判据：凡两个数需要把一个同步成另一个，
  就是两套并存，必须删一个。**

## 五、不打扰

**播报是配角，主角是用户和 AI 的对话。**

- ~~**裁决过**：播报借还背景音乐——整条删除。借了还、还了借的抖动就是这么来的
  （Claude 分批送来，批间停顿一超时就误判「说完了」还音乐，下一批到又借走）。
  音乐只归语音输入——只有它真需要麦克风安静。~~ **2026-10-21 部分改判**：
  **借还（pause/resume）仍然不回来**——抖动就出在状态来回切上。
  但「播报时把汽水音乐压到背景音量」回来了，**因为它不是借还、是改数值**：
  播报开始降 5 格、播完升 5 格（`SodaVolumeDucker`），播放状态压根没动，抖不起来。
  已知取舍：那 20 格是汽水音乐的**应用内**音量、本机读不到 → 只能相对调节，
  音量本来就低时会触底、播完升回去不等于原值。
  判据补一句：**让路优先选「改数值」而不是「改状态」**——状态切换会抖，数值不会。
- **裁决过**：字幕要不要强制——不要，配置可关。
- **裁决过**：微信链路要不要出声——不。聊天窗口里已经有文字了，再念一遍是打扰。

## 六、诚实标注边界

**做不到的事写清楚做不到，不假装能。**

- ~~**裁决过**：「掀页」在文档里怎么写——写明它**掀不彻底**：页号每批才送来，
  还没来的页拦不住。~~ **2026-10-18 作废**：页号改由助理自编，事先就有，
  掀页掀得干净，三档在所有输入形态下都成立。
- **裁决过**：自检腐烂（2026-10-16 三个用例假绿、2026-10-17 两条因日志门限假红）——
  发现即记，记的是**为什么**不是「改好了」。

## 这一层怎么用

三层里出现分歧时，顺序是：

1. **先问目的是什么**（本文）——目的是否被满足
2. 目的满足不了再看是不是需求层写错了（playback-requirements.md）
3. 再看是不是实现层能解（playback-queue.md）

**倒过来做**——先想着怎么改代码、再倒推目的——就是凑合。本文的作用就是拦住这件事。

## 维护约束

- 新增原则必须附**裁决记录**（它裁决过什么）。没有裁决记录的原则说明还没被检验过，
  写在这里只是愿望。
- 原则之间冲突时，以本文为准；发现冲突就改本文，别让两层各执一词。
