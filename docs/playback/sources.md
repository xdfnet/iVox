# 播报接入方层

> 这一层只回答一个问题：**谁在往播报队列里说话，它们各自拿得出什么。**
> 播报侧必须处理对的场景见 [需求层](requirements.md)；
> 队列怎么存、容器怎么设计**本文不谈**。
>
> 读法顺序：**目的层 → 接入方层（本文）→ 需求层 → 实现层**。有分歧先翻 [目的层](purpose.md)。
> 本文与代码不符时以代码为准，但请顺手改本文——这张表是后两层的基准。

## 共性：不管接法多不一样，塌缩后是同一种东西

术语以 [需求层](requirements.md) 为准，本文只说**各接入方送来的字段分别能决定什么**：

**队列里只有页**，页号**一律由助理自编**（`PlaybackPage.localID`），
接入方给的各种编号（Claude 的 `message_id`、pi 的 `turn`）**只进日志**——
它们不决定「这是不是一页」，也不决定「这是第几页」。
**句** = 服务自己切的合成单位（`PlaybackSentence.seq`，全局单调）。

**一条 assistant 消息 = 一页**——这条消息里同时带工具调用也算一页，不切；
那一页是什么由接入方说，助理只管发号、排队。

进队列前，所有接入方都被压成同一种形状：

```
一页（整页原文）→ 助理切成若干句 → 排队
```

**页是整页一次到手的**：接入方攒齐这一页才交，不是分批往里塞。
Claude 那边由 hook 攒（见下），pi 那边由扩展攒（`message_end` 时一次发出）。

## 对齐表（目标态）

| | 一页是什么 | 怎么交到 daemon | 现状 |
|---|---|---|---|
| **Claude Code** | 一条 assistant 消息（一个 MessageDisplay 完整页） | hook 按 `message_id` 攒着，等 `final=True` 才一次交 → `ivox speak --source claude --voice <音色>` | ✅ 整页一次 |
| **pi** | 一条 assistant 消息 | 每页调一次 `ivox speak --source pi --voice <音色>` | ✅ 整页一次 |

两家都是**整页一次**，走的是**同一个入口**（`ivox speak`）：页的边界由接入方给出，
页与页之间先来先进，不按轮分组。粒度差异（谁交得快）不影响结构。

## 接入形态（真正的来源分类）

产品名会变、会新增，**形态不会**。判定按形态走——**播报只有一个入口**
（`ivox speak`，一次调用 = 一页），所有接入方最终都落到下面四种之一：

| 形态 | 长什么样 | 谁在用 | 身份 | 结束 |
|---|---|---|---|---|
| **B. hook 攒页** | 工具渲染时按行批触发 hook，hook 攒齐一整页才交 | Claude Code（MessageDisplay） | 页号助理自编；`message_id` 只作 hook 端的攒页键 | 攒齐即交；**没有「说完了」信号** |
| **C. hook 终了一次** | 工具结束时触发 hook，payload 带完整回复 | 暂无接入方；**任何能配 stop hook 且 payload 有 `last_assistant_message` 的工具**都能接 | 同 B：一次调用 = 一页 | 发完即完整 |
| **D. 一次性 speak** | 命令行丢一段文本进来 | `ivox speak`（人工、脚本、pi 每页一次） | 一次调用 = 一页 | 发完即完整 |
| **E. 插队播报** | 用户主动开口，要立刻响 | Opt+Z 划词译文 | 无 | 发完即完整；**不进队列**，主节点暂停 + 独立节点念完接着播 |

> 原形态 A（长连接流式）**已删**（2026-11-02）：pi 改走 `ivox speak` 后没有第二个入口了。

**D 是陌生人，不插队。** 哪怕是用户自己在终端敲的，纸进了队列也没有特权，
没人说得清它是不是「你现在急着要的东西」——老老实实排队。要插队必须显式 `--now`，
那是形态 E 从命令行走的一扇门，不是陌生人忽然有了特权。

两条**不进队列**的路，别混进上面这张表：

| | 做什么 | 与队列的关系 |
|---|---|---|
| **麦克风**（按住右⌘ / 右⌃） | 录音 → 语音转文字 → 文字落到光标所在的输入框 | **只调 `pausePlayback()`**（暂停，不删内容；说完从断点接着播）。用户的讲话是给 AI 的，不是让播报员复述一遍——所以一个字都不往队列递。全项目没有任何以 `speech` 入队的调用点，这是结构事实，不是约定 |
| **微信** | `sendMessage` / `sendTyping` / 长轮询 `pollLoop` | 回复本身只发消息和「正在输入」，**永不发声**。聊天窗口里已经有文字了，再念一遍是打扰（[目的层](purpose.md) 早已裁定）。**怎么保证的**：它 spawn 的 claude 以 `--bare` 启动（跳过 settings 与插件里的所有钩子），所以**压根不触发 `MessageDisplay`**——它的回复不会流到播报队列。「不念」是结构性的，不是配置出来的，也没有开关 |

**形态 C 是一整个类别。** 任何工具只要能配一个 stop hook、payload 里带
`last_assistant_message`，就能以「整段一次」的方式接进来——这是最低门槛的接法。
目前没有接入方占着，留着这条是因为它划的是「接得进」的下限，不是某个具体产品。

## 打断粒度：不归本文管

两档按键在任何来源下**行为一致**——因为页号是助理自编的，缺的从来不是编号。
**「用户耳朵里那页是哪一页」这个事实由本文回答；按键的手劲属需求层**（见
[requirements.md 的两档一节](requirements.md)）。

## 准入标准（以后接新 agent 按这条判）

> **新端一律走 `ivox speak`**（2026-11-02）：自己攒页、自己查音色、自己拼好参数，
> 然后调一次 `ivox speak --source <自己的来源> [--voice <音色>] -- "<整页正文>"`
> （查不到音色就不带 `--voice`，服务端走默认音色）。
> 服务端只管照单念。**不要新开协议、不要新开 socket 协议分支**——
> 曾经有第二条入口（流式连接），两条入口意味着两套语义，各自在漂。
> 已经有别的端这么干了：Samantha 这类要出声的端，**自己拼参数**（`source:samantha` +
> 自己的音色），不靠 Claude Code 那个 hook（那个 hook 只服务 MessageDisplay）。
>
> **音色各端各管各的**（2026-11-02 裁决）：iVox 的 `[playback.sourceVoices]` 只管**走 iVox 自己
> 的客户端**（hook.sh 与 pi 扩展）——它们读那张表。**端自带配置的（像 Samantha 读自己的
> `Configuration.ivox.ttsVoice`）不归那张表管**，也不必改：音色是端自己的事，
> 服务端只管照单念。

必须回答三问，答不出就在实现里退化成「只能全掀」那一行（不是不接，是打断粒度退化）：

1. **一页从哪来** —— 有没有「一条 assistant 消息」的边界（message id / item id / 显式翻页信号）？
   拿不到 → 接入方整段一次交（形态 C/D），一次调用 = 一页
2. **怎么交** —— 攒齐整页一次（hook 攒或直接攒），然后调 `ivox speak --source <来源> --voice <音色>`
3. **用户中断这一轮时，已送出的页怎么办** —— 撤不了：内容照播（用户另有 `Ctrl+2` 全掀可用）。
   （曾有 `{cancel}` 按连接撤页的机制，随「唯一入口」删除——没有流，也就没有「这一轮」可撤。）

前两问决定**并页粒度**，**不影响能不能掀**——页号一律由助理自编，两档打断对任何来源都成立。
第三问决定「用户中断这一轮」时，那几页会不会照念完。

## 链路事实：Claude 那边是 hook 端攒的页

最容易误解的一处，**队列侧压根不知道 session 是什么**：

```
hook.sh 收到一批 MessageDisplay
  → 按 message_id 把这一批的正文追加进 ~/.config/ivox/pagebuf/<message_id>
  → 收到 final=True（这一页说完了）时，把整页一次性交给 daemon
```

- 攒页的键是 `message_id`，只存在 hook 端（`~/.config/ivox/pagebuf/`）；
  **队列侧不落它、不认它**。
- 一页交出去之后就没有「说完了」信号了——**队列排空即收尾**，
  不需要端再报一次。
- ⚠️ **时序假设**：hook 攒页靠的是「同一页的批次会连续到达」。
  正常交互成立；极端情况下（一页的批次被别的页的批次插在中间），
  攒页的顺序会乱。风险点在 hook 端，不在队列。

## 维护约束

- 接入方的能力边界（能不能拿到页的边界、有没有增量）是**对方工具的事实**，不是本项目的设计选择。判断依据一律回对方源码/文档查，别凭印象。
- 改接入方接线（hook 配了哪些事件、传了什么）**必须同步改本文**，并回头看 requirements.md 的场景清单还成不成立。
- 文档里每条「现状」都应能在代码或对方源码里指出出处；写不出出处的，标成待核实。
